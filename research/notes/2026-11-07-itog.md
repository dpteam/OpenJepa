# 2026-11-07 — итог: что заработало, что нет

## Итоговая конфигурация

```yaml
proj_dim: 8            # малое D: меньше шума от SIGReg
env.blur: 2.0          # anti-aliasing: гладкий сигнал
ctx: 2                 # контекст: скорость объекта
inv_weight: 0.5        # inverse-dynamics: управляемые факторы
probe_weight: 1.0      # проба z -> p: стоимость в задаче
lamb: 0.05             # вес SIGReg
```

## Числа

| метрика | до | после |
|---|---|---|
| асимметрия латента X/Y | 10.0× | **1.15×** |
| `open8` / ‖z‖ | 0.89 | **0.57** |
| ошибка пробы | 50 px | **10.3 px** |
| успех планирования | 17–25% | **50%** |

Обучение: 11 эпох из 30, `pred_loss` 0.26 → 0.069.

## Что дало наибольший вклад

По убыванию:

1. **`proj_dim: 64 → 8`** — убрал шум, который SIGReg навязывал данным
   на 2-мерном многообразии. `open8` 5.74 → 2.13.
2. **`blur=2.0`** — сделал сигнал гладким по построению. Вместе с (1):
   `open8` → 1.65.
3. **Проба `z → p` + стоимость в задаче** — убрала требование
   «дойти и остановиться». Успех 17% → 50%.
4. **`inverse-dynamics`** — вернул в латент горизонталь (асимметрия 10× → 1×).
5. **`ctx=2`** — без него предиктор не видит скорость, `pred_loss`
   застревает на 0.33.

## Что не заработало

### Метрическая регуляризация

`loss_metric` держится на 1.0 (значение для несвязанных величин) во всех
прогонах, даже когда весит больше `pred_loss`. Причина — прямой конфликт с
SIGReg: чтобы заполнить `D−k` измерений шумом, энкодер обязан нарушить
метрику. См. `2026-11-06-sigreg-vs-metric.md`.

### LayerNorm + variance_floor вместо BatchNorm

Латент схлопывался (`val_std` 0.0008). Финальный `Linear` проектора может
обнулить веса, а градиент `variance_floor` в этой точке слишком слаб против
`pred_loss`. Оставлено как опция `proj_norm`, но по умолчанию BN.

### Stop-gradient на цели

В sweep разница с baseline была в пределах шума. Не используется.

## Открытые вопросы

1. **`open8` / ‖z‖ = 0.57** — всё ещё выше порога 0.5. Планировщик работает
   на грани.
2. **50% успеха** — на игрушке это мало. Нужно понять, это предел метода
   или данных.
3. **Планирование в `probe`-режиме** использует обученный readout. Это
   честно, но теряет главное преимущество JEPA — «нет декодера». Для
   реальных задач нужен латент, который сам является метрикой.
