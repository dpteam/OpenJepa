# 06. Планирование и управление

## 1. Коротко

Модель мира отвечает на вопрос «что будет, если…». Планировщик задаёт вопрос
«а что мне сделать, чтобы стало хорошо?» — и отвечает на него перебором
вариантов в латентном пространстве.

```
найти  a_{t..t+H-1}
такие что  Cost(z_H) минимальна
где  z_{k+1} = Pred(z_k, a_k)
```

Это классическая задача оптимального управления. Отличие от robotics-стека
в том, что `Pred` — нейросеть, а `z` — латент, а не состояние.

---

## 2. Почему планировать в латенте

### 2.1 Сравнение

| Подход | Что перебираем | Стоимость одного шага |
|---|---|---|
| Планирование в пикселях | будущие кадры | генеративная модель: секунды |
| Планирование в состоянии | физические переменные | нужна известная модель среды |
| **Планирование в латенте** | **эмбеддинги** | **один forward предиктора: микросекунды** |

Конкретное число: **LeWorldModel** (15M параметров, обучение на одной GPU
за несколько часов) планирует до **48× быстрее** world-моделей на
фундаментных моделях [arXiv:2603.19312].

Причина проста: предиктор — это `MLP` над вектором 64–256 чисел. Один forward
дешевле, чем один шаг видео-диффузии, на 3–4 порядка.

### 2.2 Что теряется

Латент не содержит всей информации о сцене. Значит:

* нельзя наложить жёсткие физические ограничения (коллизии) напрямую;
* нельзя гарантировать, что план исполнится в реальности;
* нужен внешний safety-слой (`03-arhitektura.md`, §4.7).

Это осознанный размен: скорость и абстракция против гарантий.

## 3. CEM: как это работает

### 3.1 Алгоритм

```
вход: z_0, цель z_g, горизонт H, N сэмплов, E элитных, I итераций

μ ← 0, σ ← init_std
для i = 1..I:
    A ← μ + σ·ε,  ε ~ N(0,I),  A ∈ R^{N×H×A}     # N вариантов
    A ← clip(A, -1, 1)
    C ← cost(rollout(z_0, A))                    # N стоимостей
    E ← лучшие E по C
    μ ← mean(E)
    σ ← std(E) (не ниже min_std)
вернуть лучший A
```

### 3.2 Код

`planning/cem.py`, метод `plan`:

```python
for _ in range(cfg.iters):
    noise = torch.randn(b, n_samples, horizon, action_dim)
    samples = (mean[:, None] + std[:, None] * noise).clamp(low, high)
    cost = self._cost(z0, goal, samples)          # (B,S)
    elite = cost.topk(n_elite, largest=False).indices
    ...
```

Три итерации, 256 сэмплов, 32 элитных — на нашей игрушке этого достаточно,
чтобы дойти до цели с точностью < 0.25 в латентной метрике (см.
`tests/test_planner.py::test_planner_reaches_goal`).

### 3.3 Функция стоимости

```python
dist = ‖z_t - z_goal‖²
cost = Σ_t w_t · dist_t  +  λ_a·mean(a²)  +  λ_s·mean((Δa)²)
```

Три компонента решают три разные проблемы:

| Компонент | Что предотвращает |
|---|---|
| `Σ w_t·dist` | уход от цели |
| `λ_a·mean(a²)` | огромные действия «в последний момент» |
| `λ_s·mean(Δa²)` | дребезг (быстрое чередование `+1/-1`) |

Без третьего компонента CEM регулярно находит решения вида
`[+1, -1, +1, -1, ...]`, которые формально хороши, но физически бессмысленны.

### 3.4 Почему не градиентный спуск по действиям

Среда за предиктором недифференцируема:

* отскоки (разрыв производной);
* контакты (переключение режима);
* ограничения (`clip` обнуляет градиент на границе).

CEM не требует дифференцируемости и естественно работает с `clip`.
Цена — больше forward-проходов, но каждый проход дешёвый.

## 4. MPC: план устаревает

### 4.1 Проблема

План на 8 шагов строится в предположении, что модель мира точна. Через
один шаг реальность отклоняется (шум, неточность энкодера, невидимое
препятствие), и остальные 7 шагов плана становятся неверными.

### 4.2 Решение: receding horizon

```
пока эпизод не кончился:
    план ← CEM(z_t, z_g, H)
    исполнить план[0]
    t ← t + 1
```

Планируем на `H`, исполняем 1. Это `LatentMPC` в `planning/mpc.py`.

### 4.3 Компромисс по частоте

`MPCConfig.plan_every` задаёт, через сколько шагов перепланировать:

| `plan_every` | Латентность | Качество |
|---|---|---|
| 1 | максимальная | лучшее |
| 2–4 | средняя | приемлемое |
| `≥H` | минимальная | открытый контур, деградирует |

В нашем коде по умолчанию 1.

## 5. Иерархическое планирование

### 5.1 Проблема одного горизонта

Один предиктор не может быть одновременно:

* точным на 100 мс (нужны быстрые детали);
* осмысленным на 10 с (нужна абстракция).

Если горизонт короткий — планировщик не видит долгосрочных последствий.
Если длинный — ошибка предсказания накапливается и план становится мусором.

### 5.2 Решение: пирамида

```
┌─────────────────────────────────────────────────────┐
│ Уровень 2 (10 с):  «дойти до двери»                 │
│   Pred_2: z_t → z_{t+16}                            │
└───────────────────────┬─────────────────────────────┘
                        │ подцель z*_1
┌───────────────────────▼─────────────────────────────┐
│ Уровень 1 (1 с):   «обойти стол»                    │
│   Pred_1: z_t → z_{t+4}                             │
└───────────────────────┬─────────────────────────────┘
                        │ подцель z*_0
┌───────────────────────▼─────────────────────────────┐
│ Уровень 0 (100 мс): «повернуть на 5°»               │
│   Pred_0: z_t → z_{t+1}                             │
└───────────────────────┬─────────────────────────────┘
                        │ действие a_t
                        ▼
```

Каждый уровень решает **свою** задачу оптимизации:

```
a*_2 = argmin Cost_2(rollout_2(z, a), z_goal)
z*_1 = первая точка траектории a*_2
a*_1 = argmin ‖rollout_1(z, a) - z*_1‖
z*_0 = первая точка траектории a*_1
a*_0 = argmin ‖rollout_0(z, a) - z*_0‖
```

### 5.3 Почему это лучше плоского планирования

Эмпирика из H-JEPA [arXiv:2610.06805]:

| Метрика | Плоский JEPA | H-JEPA (3 уровня) |
|---|---|---|
| Успех на Visual AntMaze | 18% | **73%** |
| Бюджет планирования | базовый | **меньше** |

Выигрыш дают два независимых эффекта (это проверено абляциями):

1. **временная декомпозиция** — короткие горизонты на нижних уровнях;
2. **абстрактные цели** — верхний уровень отбрасывает быстрые детали.

### 5.4 Реализация

`models/hierarchy.py`: один общий энкодер, отдельный предиктор на каждый
уровень, обучение на парах `(z_t, z_{t+s})` с макро-действием (среднее по
окну `s`).

Планировщик для иерархии в коде пока не выделен в отдельный класс — это
пункт `ROADMAP.md`. Логика описана выше и реализуется поверх `CEMPlanner`
одним циклом по уровням.

## 6. Планирование против RL и имитации

| Подход | Что нужно | Плюсы | Минусы |
|---|---|---|---|
| **RL** (PPO, SAC) | reward, много взаимодействий | учится на опыте | дорого, нестабильно, нужен reward |
| **Имитация** (BC) | экспертные демонстрации | просто, быстро | не обобщает за пределы демонстраций |
| **Планирование в модели** | модель мира | ноль взаимодействий, смена цели на лету | страдает от ошибок модели |
| **Планирование + дистилляция** | модель мира + планы | быстрое исполнение + качество планов | двухстадийность |

Наша архитектура использует последний вариант: CEM строит планы, политика
(System 1) учится их воспроизводить, планировщик остаётся для трудных случаев.

Это же делает **V-JEPA 2-AC**: обучение на 62 часах неразмеченного видео
DROID, затем zero-shot планирование на Franka без сбора данных в целевой
среде [arXiv:2506.09985].

## 7. Практические настройки

| Параметр | Значение в коде | Как тюнить |
|---|---|---|
| `horizon` | 8 | короче → реактивнее, длиннее → дальновиднее |
| `n_samples` | 256 | больше → точнее, линейно дороже |
| `n_elite` | 32 | 10–15% от `n_samples` |
| `iters` | 3 | 2–5; больше — обычно без пользы |
| `init_std` | 0.6 | 0.5–1.0; зависит от масштаба действий |
| `min_std` | 0.05 | не даёт «застрять» |
| `discount` | 0.95 | 0.9–0.99 |

**Правило:** если планировщик не сходится, сначала увеличьте `n_samples`,
потом `iters`, и только потом трогайте `horizon`.

## 8. Главная опасность: эксплуатация ошибок модели

Планировщик оптимизирует **предсказание**, а не реальность. Если предиктор
где-то ошибается выгодным образом, CEM найдёт эту ошибку и будет её
использовать. Это классический **reward hacking**, только награда — стоимость.

Симптомы:

* в латенте план отличный, в реальности — нет;
* действия выглядят «странно» (например, мяч удерживается у самой стены);
* успех в симуляторе не переносится.

Лечение:

1. **Короткий горизонт** — меньше пространства для эксплуатации.
2. **Ансамбль предикторов** — стоимость = среднее + штраф за разброс
   (как в PETS/MBPO).
3. **Регуляризация на правдоподобие действий** — не разрешать действия,
   далёкие от обучающего распределения.
4. **Проверка на реальной среде** — обязательна, никакая метрика в латенте
   её не заменяет.
