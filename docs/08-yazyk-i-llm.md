# 08. Язык и LLM: мост, а не ядро

## 1. Коротко

Язык нужен системе по двум причинам: чтобы **понять человека** и чтобы
**объяснить себя**. Ни та, ни другая не требует, чтобы язык был субстратом
мышления.

Наша позиция:

```
LLM  = интерфейс + хранилище абстрактных понятий
JEPA = модель мира + планировщик
```

LLM не решает, как двигать рукой. Он переводит «поставь чашку слева от
тарелки» в точку латентного пространства, а потом объясняет, что получилось.

---

## 2. Два направления

```
            ┌──────────────────────────────────────────┐
  текст ───>│ TextEncoder ──> Adapter ──> z_goal       │──> планировщик
            └──────────────────────────────────────────┘
                              «понять»

            ┌──────────────────────────────────────────┐
  z_t   ───>│ Adapter⁻¹ ──> LLM ──> текст              │──> человеку
            └──────────────────────────────────────────┘
                              «объяснить»
```

Оба направления используют **один и тот же** адаптер (в идеале — ортогональное
преобразование, см. §3).

---

## 3. Платоновское выравнивание: почему достаточно поворота

### 3.1 Теорема

Balestriero & LeCun [arXiv:2610.39302] доказывают:

> Если два JEPA обучены на разных модальностях, и их положительные пары —
> это два наблюдения одной сцены («хорошие виды»), то выученные
> представления совпадают **с точностью до одного ортогонального
> преобразования**.

Формально: существуют энкодеры `Enc_A`, `Enc_B` и ортогональная матрица `R`
такие, что

```
Enc_A(x) ≈ R · Enc_B(y)     для пар (x, y) одной сцены
```

### 3.2 Что это даёт на практике

Не нужно учить сложный кросс-модальный адаптер. Достаточно оценить **одну
матрицу поворота**. Это задача Ортогонального ПроКруста:

```
R* = argmin_R ‖ Z_text · R - Z_image ‖_F ,   RᵀR = I
```

Решение в замкнутой форме через SVD:

```python
M = Z_text.T @ Z_image
U, S, Vt = torch.linalg.svd(M)
R = U @ Vt          # ортогональная матрица поворота
```

Всё. Никакого обучения с градиентами, никаких миллионов пар.

### 3.3 Подтверждение из статьи

Авторы показывают, что после одного поворота раздельно обученные энкодеры
превращаются в **image captioner** с CIDEr **0.838** на COCO — без
дополнительного обучения.

А на pair-free бенчмарке текстовый JEPA (109M) даёт **64%** top-5 на
ImageNet-100 против максимум **56%** у языковых моделей до 8B.

### 3.4 Важная оговорка

«С точностью до поворота» — это про **геометрию представления**, а не про
умение решать задачи. Совпадение направлений не означает, что текстовая
модель умеет считать, а визуальная — ходить. Это разные способности.

## 4. Как обучать мост

### 4.1 Данные

Минимально достаточно пар «наблюдение ↔ описание»:

* видео + субтитры;
* изображение + подпись;
* траектория робота + инструкция.

Ключевое требование: пары должны быть **двумя видами одной сцены**, а не
двумя разными сценами. Иначе теорема не применяется, и выравнивание
получается плохим (это и есть «плохие виды» next-token prediction).

### 4.2 Три режима обучения

| Режим | Что делаем | Когда использовать |
|---|---|---|
| **Procrustes** | оценить `R` по SVD на парах | есть парные данные, энкодеры уже обучены |
| **Контрастивный** | InfoNCE между `z_text` и `z_img` | пар много, нужен устойчивый мост |
| **Регрессия** | `‖Adapter(z_text) - z_img‖²` | пар мало, есть сильный текстовый энкодер |

Наш выбор по умолчанию — Procrustes: дёшево, интерпретируемо, не портит
исходные представления.

### 4.3 Проверка качества моста

Метрики (по убыванию строгости):

1. **Retrieval** — насколько часто правильная пара попадает в топ-k.
2. **Циклическая согласованность** — `decode(encode(text)) ≈ text`.
3. **Downstream** — решает ли система задачу по текстовой инструкции.
4. **Человеческая оценка** — понятны ли объяснения.

## 5. Композициональные инструкции

Одна инструкция часто содержит несколько подзадач:

> «Возьми чашку, поставь её слева от тарелки и не задень ноутбук».

LLM разбирает это на план:

```json
[
  {"action": "grasp", "target": "cup", "constraint": "gentle"},
  {"action": "move",  "target": "left_of:plate"},
  {"action": "avoid", "target": "laptop"}
]
```

Каждый шаг отображается в `z_goal` через адаптер. Планировщик решает каждый
по очереди (или совместно, если ограничения общие).

**Что здесь делает LLM:** только декомпозицию. Он не знает, где находится
чашка — это знает энкодер. Он не знает, дотянется ли рука — это знает
планировщик.

### 5.1 Ограничение по времени

Декомпозиция должна происходить **до** начала движения (или на паузах).
Если LLM вызывается на каждом шаге, латентность вырастает с миллисекунд до
сотен миллисекунд, и контур управления разваливается.

Правило: LLM — на границе задач, не внутри цикла управления.

---

## 6. Почему LLM не должен решать физику

Три причины, каждая достаточна:

**(а) У него нет доступа к состоянию.** LLM видит текст, а не латент. Всё,
что он знает о сцене, прошло через чьё-то описание — с потерями.

**(б) Он не калиброван.** LLM уверенно говорит «мяч долетит», не имея
механизма проверки. Модель мира даёт число (ошибку предсказания), которое
можно сравнить с порогом.

**(в) Он медленный.** Один вызов — десятки-сотни миллисекунд. Контур
управления работает на 10–100 Гц.

## 7. Обратное направление: объяснения

`z → текст` нужен для:

* **доверия** — человек видит, что система «поняла» задачу;
* **отладки** — почему план такой;
* **обучения** — объяснения можно использовать как слабую разметку.

Простейшая реализация: ближайшие эпизоды из памяти + текущий латент →
в промпт LLM → текст. Это не «чтение мыслей», но работает.

Честная оговорка: объяснение **post-hoc**. Оно не обязано отражать реальный
процесс принятия решения. Не путайте объяснение с механизмом.
