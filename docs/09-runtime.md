# 09. Рантайм и инференс

## 1. Коротко

Рантайм — это то, что превращает чекпоинт в работающую систему. Три вещи,
которые он должен делать хорошо:

1. **Быстро кодировать наблюдение** — один forward энкодера.
2. **Быстро планировать** — CEM в латенте, десятки миллисекунд.
3. **Не падать** — таймауты, деградация, безопасные значения по умолчанию.

Всё остальное (HTTP, батчинг, метрики) — обвязка.

```
                    │       │ z                        ▼       │
                    │  ┌────┴─────┐              ┌──────────┐  │
                    │  │  memory  │              │  act()   │  │
                    │  └──────────┘              └────┬─────┘  │
                    └──────────────────────────────────┼────────┘

                                                       ▼
                                              ┌─────────────────┐
                                              │  Исполнитель    │
                                              └─────────────────┘
```

Класс: `runtime/engine.py::OpenJEPAEngine`.

## 3. API

### 3.1 Python

```python
from openjepa.runtime import OpenJEPAEngine, RuntimeConfig

eng = OpenJEPAEngine.from_checkpoint("runs/toy/best.pt", RuntimeConfig(device="cuda"))
eng.reset()
eng.set_goal(goal_frame)          # цель кодируется один раз

for frame in camera:
    action, surprise = eng.step(frame)
    robot.apply(action)
```

Три метода, которые надо знать:

| Метод | Что делает | Когда вызывать |
|---|---|---|
| `set_goal(frame)` | кодирует цель в латент | один раз (или при смене цели) |
| `step(frame)` | кодирует кадр, считает `surprise`, планирует, выдаёт действие | каждый шаг |
| `reset()` | очищает историю | в начале эпизода |

**Почему `step()`, а не `act()` + `surprise()`.** Каждый вызов добавляет кадр
в историю контекста. Если вызвать оба на одном наблюдении, кадр попадёт
в историю дважды, «производная» (разность латентов) исказится вдвое, и
планировщик начнёт ошибаться. `step()` гарантирует ровно одно добавление.
Обёртки `act()` и `surprise()` оставлены для отладки, но в цикле управления
используйте `step()`.

**Почему `set_goal()` отдельно.** Иначе каждый шаг тратит целый forward
энкодера на перекодирование одной и той же цели — это сопоставимо по
стоимости с самим планированием.

### 3.2 CLI

```bash
python -m openjepa.runtime.cli train --config configs/pretrain_toy.yaml
python -m openjepa.runtime.cli eval  --ckpt runs/toy/best.pt --episodes 20
python -m openjepa.runtime.cli demo  --ckpt runs/toy/best.pt --out runs/demo.png
python -m openjepa.runtime.cli serve --ckpt runs/toy/best.pt --port 8077
```

### 3.3 HTTP

```
GET  /health                       -> {"ok": true}
POST /act                          -> {"action": [0.12, -0.44], "surprise": 0.031}
     {"frame": "<base64>", "goal": "<base64>"}
```

Сервер на стандартной библиотеке — без FastAPI/uvicorn. Внутри есть `Lock`
(движок не потокобезопасен) и кэш цели: если `goal` не изменился, он не
перекодируется. Для продакшена этого мало (нет пула воркеров, метрик,
graceful shutdown), но для проверки идеи достаточно.

## 4. Бюджет латентности

Типичные значения для нашего toy-конфига (2.72M энкодер + 4.71M предиктор).
Замеряется `tools/bench.py`.

| Операция | Порядок | Комментарий |
|---|---|---|
| `encode` (1 кадр 64×64) | единицы мс | ViT-6 слоёв, 64 токена |
| `predict_next` (1 шаг) | < 1 мс | MLP 384 |
| CEM (H=8, S=256, 3 итерации) | десятки мс | 6144 forward предиктора |
| **полный цикл** | **десятки мс** | 20–50 Гц на GPU |

Пропускная способность растёт линейно с батчем: планировщик уже батчевый
(`(B,S,H,A)`), поэтому 8 роботов считаются почти так же быстро, как один.

Точные числа на вашей машине:

```bash
python tools/bench.py --ckpt runs/toy/best.pt
```

## 5. Как ускорять

### 5.1 По порядку выгоды

| Приём | Ускорение | Сложность |
|---|---|---|
| `torch.inference_mode()` | 1.1–1.3× | уже сделано |
| bf16/fp16 | 1.5–2× на GPU | одна строка |
| `torch.compile` | 1.3–2× | одна строка, но долгий прогрев |
| Уменьшить `n_samples` в CEM | линейно | качество падает |
| Уменьшить `horizon` | линейно | теряется дальновидность |
| Кэш энкодера по кадрам | до 2× | нужно следить за памятью |
| ONNX / TensorRT | 2–4× | экспорт, потеря гибкости |
| Квантование (int8) | 2–3× | нужна калибровка |

### 5.2 Что не надо оптимизировать

Энкодер почти никогда не является узким местом в контуре управления: он
вызывается 10–30 раз в секунду, а планировщик — сотни раз на решение.
Сначала оптимизируйте CEM.

### 5.3 Крайний случай: edge

**LeWorldModel** — 15M параметров, обучается на одной GPU за несколько часов,
планирует в 48× быстрее фундаментных world-моделей [arXiv:2603.19312].
Такая модель помещается на смартфон или робота и работает без облака.

Наш toy-конфиг (7.6M) — тот же порядок.

## 6. Управление состоянием

`Engine` хранит:

```python
self._prev_obs      # предыдущий кадр (для surprise)
self._prev_action   # предыдущее действие
self._prev_latent   # предыдущий латент
```

### 6.1 Проблемы

* **Потокобезопасность.** `Engine` не потокобезопасен: два потока,
  вызывающие `step()` на одном объекте, испортят состояние. В HTTP-сервере
  это решено `threading.Lock` вокруг `set_goal` + `step`. Для нескольких
  параллельных клиентов лучше пул движков.
* **Утечка между эпизодами.** Обязательно вызывать `reset()` перед новым
  эпизодом, иначе история и `surprise` считаются от чужого кадра.
* **Двойное добавление кадра.** Вызов `act()` и `surprise()` на одном
  наблюдении добавляет кадр в историю дважды. Используйте `step()`.
* **Долгие эпизоды.** `deque(maxlen=ctx)` не растёт, но `_prev_action`
  и цель живут, пока не вызван `reset()`.

### 6.2 Рекомендуемая схема для сервиса

```
пул из K движков (K = число параллельных клиентов)
  ├── каждый со своим состоянием (история + цель)
  ├── Lock на время step()
  └── периодический reset по таймауту простоя
```

## 7. Отказоустойчивость

| Отказ | Симптом | Что делать |
|---|---|---|
| Кадр не пришёл | таймаут | вернуть предыдущее действие (hold) |
| Кадр битый | NaN в энкодере | пропустить кадр, инкремент счётчика |
| Планировщик не успел | нет ответа за бюджет | вернуть лучшее из предыдущего плана |
| `surprise` аномально высок | модель «не понимает» | перейти в безопасный режим (стоп) |
| GPU OOM | исключение | fallback на CPU-модель |

**Правило:** любая ветка отказа должна возвращать **безопасное** действие,
а не исключение. Робот, который падает с трейсбеком, опаснее робота, который
остановился.

## 8. Мониторинг

Метрики, которые надо логировать всегда:

| Метрика | Зачем |
|---|---|
| `surprise` (p50, p99) | детектор «мир изменился» |
| латентность `encode` / `plan` | SLA |
| распределение действий | залипание, дребезг |
| доля срабатываний медленного контура | насколько система «думает» |
| частота fallback'ов | здоровье пайплайна |

Тревога, если:

* `surprise` p99 вырос в 3 раза → сдвиг домена или поломка камеры;
* доля медленного контура > 50% → модель мира не справляется;
* распределение действий сжалось в точку → политика залипла.
