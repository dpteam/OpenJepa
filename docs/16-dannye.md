## 1. Коротко

Для первой модели (модель мира на видео) нужны **видео с действиями**, а не
текст. Текст полезен позже — для языкового моста. Поэтому приоритет:

```
1. Видео + действия  → модель мира (фазы 1–2, 6)
2. Текст             → языковой мост (фаза 5)
3. Код               → отдельная ветка, не для JEPA
```

Локальные архивы закрывают пункт 2 (и частично 3). Пункт 1 придётся качать.

## 3. Сколько места нужно на самом деле

### 3.1 Модель мира (видео)

| Этап | Данные | Размер | Комментарий |
|---|---|---|---|
| Прототип | 10–50 ч видео 256×256 | 20–100 GB | хватит для первых результатов |
| Рабочий | 500–1000 ч 256×256 | 1–2 TB | сравним с DROID (62 ч) × 10 |
| Полный | 10 000 ч 256×256 | 10–20 TB | уровень V-JEPA 2-AC |

**Важно:** хранить видео в 64×64/128×128 бессмысленно (потеря деталей), а в
4K — бессмысленно (модель всё равно даунсемплит). Оптимум для обучения:
**256×256, 30 fps, h264, ~1–2 Мбит/с** → 0.5–1 GB на час.

При 104 GB свободных на `I:` реалистично:
* 100–200 часов видео в 256×256 — хватит на прототип и первые сравнения.

Если понадобится больше — либо чистить `E:`/`G:` (там 42/57 GB свободно),
либо внешний диск.

### 3.2 Текст (языковой мост)

Для Procrustes-выравнивания достаточно **пары сотен тысяч пар**
«наблюдение ↔ описание». Это:

* 1–5 GB текста (Википедия RU в ZIM — 38 GB вместе с картинками, чистого
  текста ~4 GB);
* или 50–100 MB пар «изображение–подпись» (COCO captions — 1 GB).

**450 GB FB2 не нужны.** Они пригодятся, только если делать свою языковую
модель с нуля, а это отдельный проект.

## 4. ZIM-читатель

`tools/zim_reader.py` — чистый Python, без libzim. Поддерживает ZIM v6,
сжатие LZMA и Zstandard, редиректы.

```bash
pip install zstandard

python tools/zim_reader.py info  <zim>
python tools/zim_reader.py check <zim>          # проверка целостности
python tools/zim_reader.py list  <zim> --limit 20
python tools/zim_reader.py text  <zim> "Python" --out article.txt
```

### 4.1 Что проверено

| Архив | Размер | Статей | Кластеров | Результат |
|---|---|---|---|---|
| gutenberg_ru_all_2026-01 | 0.01 GB | 209 | 6 | ✅ все кластеры, все dirent'ы |
| wikipedia_ru_all_maxi_2025-06 | 38.39 GB | 7 582 462 | 66 070 | ✅ выборка 500 статей, 214 редиректов |

Дополнительно: 60 статей подряд проверены на совпадение
`dirent.title` ↔ `<title>` в HTML — **60/60**.

### 4.2 Три бага, которые пришлось исправить

Найдены при проверке на реальных файлах — ровно то, ради чего писался `check`:

1. **Кластер сжимается целиком.** Байт сжатия, затем *весь* блок (оглавление +
   данные) — один zstd-фрейм. Если читать оглавление из сжатых данных,
   получаешь мусор.
2. **Оглавление кластера самоописываемое.** Первое `uint32` — это и размер
   заголовка, и смещение первого блоба. `n_offset = first / 4`. Не «количество
   блобов в начале».
3. **Редиректы короче на 4 байта.** У записи с `mimetype == 0xFFFF` после
   `revision` идёт `redirectIndex` (4 байта), и сразу url. Если читать как
   обычную запись (16 байт), url сдвигается и «кластер» становится мусором.

Все три — типичные примеры «формат описан в вики, но детали в исходниках».
Сверялись с `openzim/libzim`, `src/cluster.cpp` и `src/dirent.cpp`.

## 6. Куда класть

```
I:\OpenJepa_DataSet\
  raw\              # как скачано (не трогать)
  video\            # перекодировано в 256x256, h264
  text\             # JSONL с текстами
  pairs\            # (видео/кадр, подпись)
  cache\            # латенты, препроцессинг
```

Правила:

* `raw/` — только чтение, никогда не модифицировать;
* всё остальное можно пересоздать скриптом;
* в git — только манифесты (`*.jsonl` со списком файлов и хешами).
